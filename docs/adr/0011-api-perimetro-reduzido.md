# ADR-0011: API NestJS restrita a entitlements, LGPD e health — sync e consent diretos via Supabase SDK

- **Status:** Aceita
- **Contexto:** O C4 nível 3 (`docs/c4/03-componentes-api.md`) desenhava a API NestJS com `SyncModule` e `ConsentModule` além de `EntitlementsModule` e `LgpdModule`, todos atrás de uma camada de repositório Prisma com RLS. A migração `20260726121100_grants_defesa_em_profundidade.sql` (já implementada na Fase 1), no entanto, concede `select, insert` ao papel `authenticated` diretamente sobre `diary_events` e `consent_events` — só faz sentido se o cliente grava nessas tabelas diretamente via Supabase SDK/PostgREST, autenticado com o próprio JWT do Supabase Auth, protegido por RLS (`auth.uid()`). Já `entitlements` tem `insert/update/delete` revogados de `authenticated` (só leitura), e `purchase_receipts`/`storylet_kill_switch` têm zero acesso de cliente — essas só podem ser escritas por `service_role`, ou seja, exclusivamente pela API. ADR-0002 já apontava a razão de fundo: projeto solo, orçamento de engenharia (R-002) não comporta reinventar sync/RLS que o Supabase já resolve de graça.
- **Decisão:** A API NestJS (`apps/api`) implementa apenas os módulos que exigem `service_role` ou lógica de servidor: `EntitlementsModule` (valida recibo Apple/Google/Stripe e agrega `origem`, ADR-0005), `LgpdModule` (exportação integral e exclusão de conta em até 15 dias, RF-091/092 — requer agregar dados possivelmente entre tabelas com regras que o próprio usuário não deveria poder disparar por escrita direta) e `HealthModule`. Diário (`diary_events`) e consentimento (`consent_events`) são sincronizados pelo cliente diretamente via Supabase SDK, sem passar pela API. `AuthModule` não emite JWT próprio — a sessão é a do Supabase Auth (magic link); a API só valida esse JWT nos guards para os módulos que possui. O C4 nível 3 é atualizado para remover `SyncModule` e `ConsentModule` do container da API.
- **Consequências:**
  - Positivas: API menor, sem camada de repositório própria concorrente com RLS do Postgres; nenhuma duplicação de política de autorização entre Prisma e RLS; sync do diário ganha offline-first "de graça" via Supabase Realtime/PostgREST sem código de servidor adicional.
  - Negativas: qualquer lógica de validação de evento de diário que não possa ser expressa como RLS/constraint de banco (ex.: regras de negócio complexas de ADR-0002) precisa virar trigger/constraint SQL, não código NestJS — trade-off aceito porque a validação de posse já é feita por trigger (`tg_diary_events_valida_propriedade`).
- **Alternativas consideradas:**
  - Manter o desenho original do C4 (Prisma + Sync/ConsentModule na API) — descartada por contradizer os GRANTs já mergeados e por adicionar uma segunda camada de autorização redundante com RLS, sem benefício concreto para um projeto solo.
- **Referências:** ADR-0002, ADR-0005, ADR-0006, RF-091, RF-092, `docs/database/migrations/20260726121100_grants_defesa_em_profundidade.sql`.
